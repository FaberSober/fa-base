# ADR-003：可选多租户模式与租户化 RBAC

- 状态：Proposed
- 日期：2026-09-17
- 范围：`fa-core` 租户基础能力、`fa-base` 租户管理、RBAC、后台管理页面及业务 Entity 约定
- 关联配置：`fa.setting.tenant.enabled`

## 1. 背景

系统原有 RBAC 在单租户场景下运行良好。接入多租户后，需要同时处理用户租户关系、角色范围、当前租户上下文和业务数据隔离。

同时，项目中存在遗留的 `com.faber.core.tenant.bean.TnBase*Entity` 层级，与当前实际使用的 `com.faber.core.bean.BaseTn*Entity` 层级重复，且 `tenantId` 类型不一致。继续并存会导致租户拦截器、自动填充和业务 Entity 继承关系不明确。

项目还需要通过 `FaSetting` 的租户开关支持单租户和多租户部署，避免不需要多租户的项目在业务代码中重复增加租户判断。

## 2. 决策

采用“一套框架代码、两种启动模式、核心层自动隔离”的方案：

1. 删除遗留的 `com.faber.core.tenant.bean.TnBaseEntity`、`TnBaseCrtEntity`、`TnBaseUpdEntity`、`TnBaseDelEntity`，统一使用 `com.faber.core.bean.BaseTn*Entity` 系列。
2. 租户 ID 统一使用 `String`，与当前租户表主键和 `BaseContextHandler` 保持一致。
3. `fa.setting.tenant.enabled` 作为应用启动时的部署模式配置，不支持运行时热切换。
4. 租户私有业务表继承 `BaseTn*Entity` 后，由核心层自动完成租户上下文、查询隔离和插入填充。
5. 平台表和控制面表不依赖通用租户拦截器，由租户管理和权限服务显式校验。
6. 对需要支持未来切换的租户业务表，采用统一 Schema：表中保留 `tenant_id` 字段；单租户模式关闭隔离，多租户模式启用隔离。
7. 权限采用三层范围：平台权限全集 `A`、租户可用权限 `C_t`、角色实际权限 `B_r`。其中 `C_t ⊆ A`，租户角色必须满足 `B_r ⊆ C_t`。
8. 租户管理员可以在当前租户的 `C_t` 范围内给租户角色分配全部权限，不再额外限制为管理员当前已拥有的权限；平台角色仅由平台管理员维护。
9. 创建租户时初始化租户权限范围、租户管理员角色、默认角色权限和创建人绑定关系。

## 4. 开发说明

### 4.1 统一 Entity 基类

- 以 `com.faber.core.bean.BaseTnCrtEntity`、`BaseTnUpdEntity`、`BaseTnDelEntity` 为唯一租户 Entity 层级。
- 删除遗留 `com.faber.core.tenant.bean.TnBase*Entity`，同步清理 import、示例和文档引用。
- 不保留旧层级中的 `corpId` 和 `Long tenantId`，除非后续单独提出集团/公司维度需求。
- 业务 Entity 不需要重复声明 `tenantId`。

### 4.2 租户模式与上下文

- 通过 `FaSetting.isTenantEnabled()` 统一判断部署模式，通过 `TenantContext` 统一读取、设置、清理和必需租户校验。
- 登录接口和 API Token 接口统一解析 `fa-tn-tenant-id`；未指定时使用用户默认租户，普通用户无可用租户时拒绝访问。
- 单租户模式忽略 `fa-tn-tenant-id` 请求头，并确保请求结束后清理上下文。
- 多租户模式下，租户业务接口必须有有效当前租户；平台接口可以显式使用无租户上下文。
- 异步任务、定时任务和消息消费必须显式传递或恢复租户上下文。

### 4.3 自动隔离和自动填充

- `FaTenantInterceptor` 只对继承 `BaseTn*Entity` 的租户业务表生效。
- 普通 MyBatis-Plus CRUD 不要求业务 Service 手写 `tenant_id` 条件。
- 插入时从可信的 `TenantContext` 填充租户 ID，忽略客户端传入的租户 ID。
- 平台跨租户查询必须通过受保护的显式服务完成，不提供无约束的通用“忽略租户”入口。
- 自定义 XML、原生 SQL、动态表和复杂报表 SQL 需要单独确认租户条件是否生效。

### 4.4 单租户和多租户模式

- `enabled=false`：不注册租户拦截器，不要求用户绑定租户，RBAC 按现有全局角色运行。
- `enabled=true`：启用租户上下文、成员校验、租户拦截和租户角色范围。
- 使用 `BaseTn*Entity` 的表在两种模式下都应存在 `tenant_id`，以支持同一套业务代码切换。
- 如果项目明确永远单租户，可以使用普通 `Base*Entity` 并不增加 `tenant_id`；以后切换多租户时需要执行实体和数据库迁移。

### 4.5 Tenant 与 TenantUser

- `Tenant`、`TenantUser` 属于控制面数据，不直接依赖普通业务表的自动租户过滤。
- 租户业务访问前统一校验租户启用状态、有效期和用户成员关系。
- 租户创建流程应初始化租户权限范围 `C_t`、租户管理员角色、角色权限、管理员成员关系和创建人角色绑定。
- 禁用或过期租户时，拒绝新请求并清理相关会话、上下文和权限缓存。
- 成员解绑、恢复和批量变更必须限定在指定租户内。

### 4.6 租户权限与 RBAC 范围

- `A` 表示平台全部有效菜单、按钮和权限点；`C_t` 表示租户 `t` 被允许使用的权限，`C_t ⊆ A`。
- `B_r` 表示角色 `r` 实际拥有的权限；租户角色必须绑定 `tenant_id`，并满足 `B_r ⊆ C_t`。
- 租户管理员可以在当前租户的 `C_t` 范围内为租户角色分配全部权限，不要求权限集合再与管理员自身权限求交集。
- 平台角色（`GLOBAL_SUPER`、`GLOBAL`）只允许平台管理员维护；租户管理员只能维护当前租户的 `TENANT` 角色。
- 角色选择器、菜单授权和权限校验都要限制在当前租户或平台授权范围内，后端不能只依赖前端隐藏权限点。
- `C_t` 缩减后，租户角色在运行时只允许使用 `B_r ∩ C_t`；不立即物理删除历史角色权限关系。
- 用户角色关系必须按租户范围处理，不能使用全局删除覆盖用户在其他租户的角色。
- 权限缓存、当前菜单和按钮权限切换租户时必须重新计算或按租户隔离。

### 4.7 Entity 与 DDL 约定

- 租户私有表增加 `tenant_id varchar(32)`，通常建立 `tenant_id` 查询索引。
- 租户内唯一业务字段使用包含 `tenant_id` 的联合唯一约束，例如 `(tenant_id, code)`。
- `fa-flow` 的 FlowLong 官方 `flw_*` 表保留上游约定的 `varchar(50)`；Java Entity 统一使用 `String`，不追加缩短字段的迁移。
- 项目自有流程 Demo 表仍按本项目约定迁移为 `varchar(32)`。
- MySQL 和 PostgreSQL 分别维护对应目录下的 DDL，不混用方言。
- 单租户模式下 `tenant_id` 可以为空或使用明确的默认租户策略；若未来需要切换，必须在启用前完成数据归属处理。

### 4.8 管理页面适配

- 租户关闭时隐藏租户管理、租户成员和租户切换入口，避免用户看到不可用功能。
- 租户开启时，平台管理员在租户页面维护 `C_t`；租户管理员只能查看当前租户的权限范围。
- 角色权限页面只展示当前角色可分配的权限；租户角色的可分配范围为 `C_t`。
- 租户管理员不能编辑平台角色；平台角色可以隐藏或以只读方式展示。
- 平台管理员可执行跨租户运维，但操作必须明确当前目标租户并记录审计信息。

### 4.9 租户功能 SQL 编写与执行规则

- 版本升级 SQL 统一维护在 `fa-base/src/main/resources/sql/fa-base/{mysql|postgre}/`，MySQL 与 PostgreSQL 必须分别编写，禁止混用方言。
- 开发阶段的租户 DDL 暂合并到现有 `1.0.36` 版本 SQL，不为每个租户子功能单独递增版本号。
- 已执行旧版 `1.0.36` 的开发数据库，当前增量通过 `fa-base/docs/sql/` 下的手动 SQL 执行；新数据库直接执行合并后的 `1.0.36`。
- `docs/sql/` 下的手动 SQL 统一命名为 `YYYYMMDDHHmm_递增序号_SQL说明.sql`：时间表示创建时间，序号表示执行顺序，说明应明确业务内容和目标数据库。
- 同一数据库操作需要分别提供 MySQL、PostgreSQL 文件；同一时间生成的文件按序号执行，不依赖文件系统排序以外的隐式顺序。
- 手动 SQL 应尽量可重复执行，例如使用 `IF NOT EXISTS`、`IF EXISTS` 或等价保护；不得包含删表、清库等破坏性操作。
- 数据库正式发布前，再根据发布版本重新固化迁移边界；已发布版本 SQL 不再回写修改。

## 5. 数据迁移与安全边界

- 租户开关是启动配置，修改后需要重启应用；不做运行时热切换。
- 单租户切换为多租户前，先创建默认租户并回填历史业务数据的 `tenant_id`。
- 同步建立旧用户的 `TenantUser` 关系，并将旧角色归类为平台角色或默认租户角色。
- 历史租户初始化 `C_t` 时使用明确的默认权限模板或现有权限集合，不通过隐式规则扩大权限。
- 租户权限范围缩减后，运行时立即拒绝超出 `C_t` 的角色权限；权限恢复时不自动扩大角色权限。
- 多租户数据存在后，不允许直接关闭租户隔离；如确需关闭，必须先完成数据合并和安全评估。
- 升级脚本不得删除业务数据；MySQL、PostgreSQL 分别提供等价迁移脚本。

## 6. 非目标

- 不为单租户和多租户维护两套业务 Service 或 Controller。
- 不通过动态修改 Entity 注解来适配缺失的 `tenant_id` 字段。
- 不把平台表、租户表和普通租户业务表全部交给同一个自动拦截器处理。
- 不在本 ADR 中实现集团、公司、组织等第二套数据隔离维度。
- 不额外设计“管理员只能分配自己已有权限”的委派权限模型；租户管理员直接以 `C_t` 作为角色权限分配上限。

## 7. 验收标准

- 遗留 `com.faber.core.tenant.bean.TnBase*Entity` 不再被业务代码或核心配置引用。
- 单租户模式下，无租户请求头也能完成原有登录、RBAC 和业务 CRUD。
- 多租户模式下，两个租户之间的查询、插入、更新、删除、导出和权限结果相互隔离。
- 租户业务插入时自动写入当前 `tenant_id`，客户端不能伪造其他租户 ID。
- 禁用或过期租户不能继续访问租户业务。
- 用户在多个租户之间切换时，角色、菜单、按钮权限和缓存正确切换。
- 用户在一个租户中修改角色，不会覆盖其在其他租户中的角色。
- 每个租户都有独立的 `C_t`，且 `C_t ⊆ A`；租户角色权限始终满足 `B_r ⊆ C_t`。
- 租户管理员可以分配当前租户全部 `C_t` 权限，但不能修改平台角色或扩大 `C_t`。
- 创建租户时自动生成租户管理员角色、初始角色权限和创建人绑定关系。
- 租户权限缩减后，超出 `C_t` 的历史角色权限不再生效。
- 租户私有 Entity 只需继承统一 `BaseTn*Entity`，普通业务逻辑不需要增加租户判断。
- MySQL 与 PostgreSQL 的 Entity 类型、DDL、索引和迁移脚本一致且符合各自方言；FlowLong 官方表保留 `varchar(50)` 兼容约定。
- 标准 CRUD、自定义 SQL、异步任务和导出场景均有针对性验证结果。

## 8. 实施顺序

1. 清理遗留 `TnBase*Entity`，统一基类和 `tenantId` 类型。
2. 抽取租户模式、上下文和上下文清理能力，补充单租户模式测试。
3. 调整租户拦截器、自动填充和 `BaseBiz`，验证标准 CRUD 隔离。
4. 完善 `Tenant`、`TenantUser` 生命周期和成员校验。
5. 增加租户权限集合 `C_t`，并在创建租户时初始化默认权限和租户管理员角色。
6. 修正角色范围：平台角色仅平台维护，租户角色权限限制在 `C_t` 内。
7. 调整用户角色关系、权限缓存和权限校验的租户范围。
8. 适配租户管理、租户权限、成员管理、角色授权和租户切换页面。
9. 补充 Entity/DDL 模板、迁移脚本、自定义 SQL/异步任务规范和回归测试。
