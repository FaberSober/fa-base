# FA Admin 按项目检查版本与下载 JAR 执行方案

文档简介：在 `fa-app` 统一维护不同项目的 FA Admin JAR 版本，各项目通过 `fa-base` 后台检查更新并从 `fa-app` 下载。复用已有文件基础设施和版本管理流程，本期完成版本管理、检查与下载，安装替换及重启作为后续功能。

创建时间：2026-10-13。状态：👀待确认；尚未开始开发。

| 编号 | 模块 | 功能 | 功能详情 | 当前规划 | 进度 |
| --- | --- | --- | --- | --- | --- |
| 1 | fa-app / 管理端 | 服务项目管理 | 项目名称、唯一标识、启停状态，区分不同业务项目 | 本期开发 | ❌未完成 |
| 2 | fa-app / 管理端 | JAR 版本维护 | 上传 JAR、版本号、说明、发布和撤回，每版本一个包 | 本期开发 | ❌未完成 |
| 3 | fa-app | 检查和下载接口 | 按项目返回最新已发布版本，按版本 ID 下载 | 本期开发 | ❌未完成 |
| 4 | fa-base / 管理端 | 后台检查更新 | 展示本机版本、远程版本和说明，提供浏览器下载入口 | 本期开发 | ❌未完成 |
| 5 | fa-base / 管理端 | 下载到服务器 | 后台下载 JAR、展示进度、校验完整性，保留现有运行包 | 本期开发 | ❌未完成 |
| 6 | 部署 | 自动安装与重启 | 停止服务、替换、启动及失败恢复 | 后续版本 | ❌未完成 |

## 1. 整体方案

### 需求对应

| 需求 | 落地方式 |
| --- | --- |
| 在 fa-app 维护 JAR 版本，区分不同项目 | 服务项目表 + JAR 版本表，以 `projectCode` 区分项目 |
| 各项目后台检查更新 | `fa-base` 系统更新页面调用本项目后端，再请求 `fa-app` 检查接口 |
| 从 fa-app 下载最新版本 | 检查返回具体版本 ID 和下载地址，下载对应已发布 JAR |
| 复用 fa-app 已有功能 | 直接复用文件上传下载，参考 Desktop 发布流程与管理页面 |

```text
统一发布中心（部署了 fa-app）
  项目 A → A 的 JAR 版本记录
  项目 B → B 的 JAR 版本记录
           ↓ 检查接口 / 下载接口
各项目后台（fa-base 系统更新页面）
  配置发布中心地址 + projectCode
  展示当前版本 → 检查更新 → 下载最新 JAR
```

- `fa-app` 管理版本记录和文件，各业务项目不用再部署一套发布中心。
- `projectCode` 表示不同代码 / 产品项目，例如 `fa-admin`、`customer-a-admin`，不是租户 ID。同一项目多台部署可以使用同一项目标识。
- “最新”是对应项目已发布记录中最大的 `versionCode`，不按创建时间、主键或版本名称字符串排序。
- 保持当前 `fa-admin.jar` 的前后端整包结构，发布包通过 `-Pfrontend` 构建。
- 本期不增加独立更新器、静态签名站点、灰度平台或进程托管；下载完成不视为安装完成。

### 模块职责

- `fa-app`：服务项目、JAR 版本记录、发布 / 撤回、对外检查和下载接口。
- `fa-app-pages`：发布中心的项目和版本维护页面。
- `fa-base` / `fa-base-pages`：各项目后台的检查更新、服务器下载任务及进度页面。
- `fa-admin/pom.xml`：构建整包并写入项目和版本元数据；业务项目使用自己的构建配置提供这些值。
- PLAN 统一维护在 `fa-base/docs/plans`，不在各模块重复创建同一方案。

## 2. fa-app 现有能力与复用结论

| 现有实现 | 已有能力 | 本期复用方式 |
| --- | --- | --- |
| `client/entity/ClientApp.java` | `clientCode`、名称、启停等应用信息 | 参考其项目管理结构，使用专用 `projectCode` |
| `client/entity/ClientRelease.java` | 版本名称、递增版本号、说明、发布状态、时间 | 沿用版本管理字段和发布流程 |
| `client/biz/ClientReleaseBiz.java` | 草稿 / 发布 / 撤回、按应用查版本、检查更新、下载 | 参考其流程，增加 JAR 专用业务，不直接调用 Tauri 检查逻辑 |
| `client/biz/ClientReleaseArtifactBiz.java` | 草稿阶段编辑文件、限制已发布版本修改 | 沿用发布后冻结包信息的约束 |
| `client/rest/ClientUpdateController.java` | 独立更新检查与下载入口 | 沿用接口组织方式，新增服务 JAR 入口 |
| `fa-base/.../FileSaveBiz.java` | 上传、文件记录、取文件、流式下载 / 存储跳转 | 直接复用文件基础设施，不重复建文件存储 |
| `release/biz/AppReleaseBiz.java` | 从实际存储文件计算 SHA-256，清理远程存储临时文件 | 参考摘要计算实现，上传后由服务端计算 |
| `fa-app-pages/pages/admin/app/client/` | 应用列表、版本列表、上传弹窗、发布 / 撤回交互 | 沿用页面布局与公共组件，增加 JAR 页面 |

**现有版本接口不能直接用于 JAR。**

- Desktop 检查接口为 `GET /api/app/client/update/{clientCode}`，要求 `current_version` 和 `target`，下载接口为 `GET /api/app/client/download/{releaseId}/{target}`。
- 平台只支持 windows / darwin / linux，架构只支持 x86_64 / aarch64；安装包强制要求 Tauri 签名，返回值也是 Tauri 更新清单。
- APK / WGT 模型还有 Android 包名、DCloud AppID、原生基座等专用字段与校验。
- 因此复用通用文件能力、管理页面组件和业务流程；新增简单 JAR 模型，避免修改 Desktop / APK / WGT 的既有协议。
- 若后续需要统一所有类型的发布模型，再单独设计通用化，本期不为此重构现有模块。

## 3. 最小数据模型：两张表

放在 `fa-app`，建议使用 `com.faber.api.app.server` 包。

### 服务项目：`app_server_project`

- `id`：项目 ID。
- `projectCode`：唯一、稳定的项目标识。
- `name`：项目名称。
- `enabled`：是否允许检查与下载。
- `remark`：备注。
- 沿用 `BaseDelEntity` 审计字段；存在版本记录时不允许随意删除项目或修改项目标识。

### JAR 版本：`app_server_release`

- `id`、`projectId`：版本及所属项目。
- `versionCode`：项目内唯一的正整数版本序号，用于比较，例如 10001、10002。
- `versionName`：展示版本，例如 1.0.1。
- `fileId`：已有文件系统中的 JAR 文件 ID。
- `fileName`、`size`、`sha256`：实际包信息，由服务端读取 / 计算。
- `releaseNotes`：更新说明。
- `status`：DRAFT / PUBLISHED / REVOKED。
- `publishTime`：发布时间。
- 每版本一个 JAR，不增加安装包子表、平台、架构及渠道字段。
- 项目标识、项目内版本号使用数据库唯一约束；已发布版本不可换包、改版本号或删除，撤回后不再对外提供。

新增 SQL 使用现有版本升级机制，提供 MySQL / PostgreSQL 脚本和菜单。大整数 ID / 版本号在前端与跨项目接口使用十进制字符串，比较使用准确整数处理。

## 4. 发布中心页面与接口

页面放在 `frontend/apps/admin/features/fa-app-pages`，菜单建议“应用管理 → 服务 JAR 版本”。

- 项目列表：新增项目、修改名称、启停、查看版本。
- 版本列表：上传 JAR、填写版本号和说明、保存草稿、发布、撤回、下载。
- 上传复用 `UploadFileLocal`，限定 `.jar`；后端同时检查真实文件存在、大小与 JAR 基础结构，计算 SHA-256，不能只依赖前端扩展名过滤。
- 不运行用户上传的 JAR。发布前核对包内项目 / 版本元数据与记录，避免上传错项目；首期构建时补充对应元数据。
- 当前配置上传上限为 1000MB，还需核对反向代理限制和文件类型策略，不因通用上传能力存在而假定所有部署都能上传大 JAR。

以下为发布中心新增接口建议，当前尚未实现。项目和版本 CRUD 沿用 `BaseBiz` / `BaseController` 的已有端点，发布与撤回使用自定义业务方法：

| 接口 | 行为 |
| --- | --- |
| `POST /api/app/server/update/check` | 请求 `projectCode`、`currentVersionCode`，返回更新判断及最新已发布版本 |
| `GET /api/app/server/download/{projectCode}/{releaseId}` | 校验项目归属、项目启用及已发布状态，再调用 `FileSaveBiz.downloadFileById` |

检查结果包含 `hasUpdate`、`releaseId`、`projectCode`、`versionCode`、`versionName`、`releaseNotes`、`publishTime`、`size`、`sha256`、`downloadUrl`。无更新正常返回 `hasUpdate=false`；项目不存在 / 停用、服务不可达等分别返回明确错误。

- 下载固定绑定检查结果中的 `releaseId`，不提供“下载时再重新选择最新版本”的模糊行为。
- 即使知道其他项目的版本 ID，也不能通过当前项目的下载路径取得该包。
- 相对下载地址由对接端基于发布中心地址解析；存储为对象存储时，现有下载方法可能重定向到文件地址，需正确支持该存储来源。
- 管理版本记录沿用登录权限；跨项目检查与下载首期按现有公开更新接口方式提供，因此项目包需适合公开分发。若包要求私有分发，再增加项目访问凭证，凭证只存后端，不能把 `projectCode` 当成访问授权。

## 5. 各项目后台接入

实现归 `fa-base`，页面放在 `fa-base-pages` 的系统管理下。

- 本机配置 `updateServerUrl`、`projectCode`；构建时将 `projectCode`、`versionCode`、`versionName` 写入 JAR 元数据。
- 当前版本读取运行包的构建元数据，不使用 Maven 的 `1.0.0-SNAPSHOT` 判断更新；首次接入补齐发布序号。
- 页面展示当前版本；点击“检查更新”，由本项目后端调用发布中心，避免浏览器跨域，也为后续私有凭证留出后端位置。
- 找到更新后展示版本、说明、大小和下载按钮；检查失败显示原因，不能显示成“已是最新”。
- 提供“下载到电脑”：浏览器从发布中心取得 JAR，供人工部署。
- 提供“下载到服务器”：本项目后端异步下载到配置目录，例如 `update/downloads/{releaseId}/fa-admin.jar`，为后续安装准备。
- 下载到服务器使用任务 ID 和轮询进度；流式写入 `.part`，完成后核对大小、SHA-256 和项目元数据，再改为已下载。
- 下载失败可重试，同一实例不并发下载同一版本；限制下载来源、超时和磁盘空间，不能覆盖当前运行包。
- 下载按钮绑定本次检查得到的版本，不接受任意用户提供的下载 URL。
- 下载完成明确显示“已下载，尚未安装”，当前版本只有真正换包重启后才改变。

本项目后端提供当前版本、检查更新、创建下载任务、查询下载任务四类接口。浏览器只提交已检查到的版本 ID，服务器重新核对项目归属和发布信息后下载；下载状态至少包含待下载、下载中、校验中、已下载和失败。浏览器关闭或刷新后，可以重新查询任务状态。

## 6. 开发顺序与人工验收

### 按功能实施

- **功能 1：服务项目管理**。先做项目列表和编辑弹窗，配套 Entity / Mapper / Biz / Controller 与菜单 SQL；验证项目标识唯一、不同项目分别维护。
- **功能 2：JAR 版本维护**。项目下展示版本列表，接通上传、摘要计算、保存草稿、发布和撤回；同时在构建中补充项目 / 版本元数据，用实际 JAR 验证上传与发布。
- **功能 3：检查和下载接口**。按项目查找最高已发布版本号，返回固定版本下载地址；验证项目归属、停用、撤回及不存在的文件。
- **功能 4：后台检查更新**。先做当前版本与检查结果页面，接通本机配置、构建元数据读取和后端远程调用；完成浏览器下载闭环。
- **功能 5：下载到服务器**。加入下载按钮、异步任务、进度轮询与完整性校验，使用临时文件保存；验证刷新页面后仍可查看任务。
- **功能 6：后续自动安装**。本期仅保留规划，待明确实际部署和启动方式后再设计实施。

### 完成标准

- 发布中心能独立维护至少两个项目及其版本，各项目后台只识别自己的更新。
- 能从 `fa-app` 下载检查结果对应的 JAR；服务器下载完成并通过校验后，页面显示“已下载，尚未安装”。
- 当前运行版本、外置配置和数据文件在检查 / 下载过程中保持原状。
- 新增接口与页面不改变既有 Desktop、APK、WGT 发布和更新行为。

人工验收步骤：

1. 新建项目 A、B，分别上传并发布不同 JAR，检查各自版本列表和文件信息。
2. 项目 A 后台检查，只返回 A 的最新已发布版本；B 的版本号再高也不影响 A。
3. 当前版本等于 / 高于发布版本时显示无更新；草稿和撤回版本不参与最新版本选择。
4. 检查后再发布一个新版，原下载按钮仍下载检查时对应的包；撤回该版本后下载被拒绝。
5. 下载到电脑可取得正确 JAR；下载到服务器展示进度，校验后保存到下载目录，原服务继续运行。
6. 模拟文件不存在、网络中断、校验失败及磁盘不足，确认提示错误、不覆盖运行包、不修改当前版本。
7. 停用项目后检查 / 下载不可用；跨项目版本 ID 请求被拒绝。

实施时执行受影响模块编译、接口隔离和下载校验的定向验证，不默认运行完整构建或全量测试。开发完成后进度标记 🔍验证中，用户确认验证成功后改为 ✅已完成。

## 7. 后续自动安装

本期保留原人工换包、重启方式。后续若需要“下载后自动安装”，再根据实际 Linux / Windows 启动方式补充停止、替换、重启和恢复机制；该步骤需要业务进程以外的执行者。现有启动自动执行数据库 SQL，安装阶段还需确认数据库兼容性，不能将下载成功视为自动更新成功。
