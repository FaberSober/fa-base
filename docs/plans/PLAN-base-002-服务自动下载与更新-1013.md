# FA Admin 服务自动下载与更新执行方案

## 1. 推荐方案与适用范围

采用 **独立 Java 更新器 + 原有业务 JAR + 签名版本清单**。

- `fa-admin.jar` 继续包含后端和前端，整包更新，不分别部署前后端。
- 新增轻量 `fa-admin-updater.jar`，负责下载、启动主程序、切换版本和恢复；不依赖业务数据库才能运行。
- 首期以 Linux 单机、单实例 JAR 部署为基准，支持一键更新，并提供可选的定时自动安装。
- 默认自动检查、可自动下载，由管理员点击安装；无人值守安装需要明确启用并配置维护窗口。
- 更新会发生服务中断，中断时长由停止、数据库迁移和启动耗时决定。首期不承诺零停机。
- 普通 `java -jar fa-admin.jar` 仍可启动业务，但未接入更新器时页面仅提供检查信息，不允许自动安装。
- 首次接入需要一次人工部署更新器、迁移目录和调整启动入口。之后日常更新只下载业务 JAR。
- Docker 部署检测后禁用 JAR 原地安装；后续通过外部运维工具更新镜像。

Java 主程序退出后，其内部线程无法继续完成启动和恢复；即使在旧进程存活时替换磁盘 JAR，也无法使已加载的类自动切换为新版本。因此更新执行者需要独立于业务进程。

## 2. 项目现状与复用位置

- `fa-admin/pom.xml`：`frontend` profile 构建 admin、portal、h5 并复制到 `static/`；最终文件名为 `fa-admin.jar`。
- 根 `pom.xml`：Java 17、Spring Boot 3.5.14；Maven 项目版本为 `1.0.0-SNAPSHOT`，不能作为线上唯一发布序号。
- `fa-base/.../DbInitRunner.java`：启动时调用 `SystemUpdateLogBiz.initDb()`，可通过 `startDbInitOnBoot` 关闭。
- `SystemUpdateLogBiz`：已有模块顺序、数据库升级锁、SQL 版本和成功 / 失败记录。继续复用，不再另建 SQL 执行器。
- `fa-admin/src/main/resources/application.yml`：Actuator 基础路径为 `/apij/actuator`；不能直接照搬默认 `/actuator/health`。
- `fa-core/doc/shell/systemd.md`：已有 Linux 服务部署说明；目前 systemd 直接启动业务 JAR，接入后调整为启动更新器。
- `fa-app` 已有移动应用发布方案；服务 JAR 的停机、数据库及回滚语义不同，首期独立定义服务发布协议。

## 3. 进程职责与部署目录

```text
systemd / 启动脚本
        ↓
fa-admin-updater.jar（常驻，唯一业务进程管理者）
        ↓
指定版本的 fa-admin.jar（业务 API + Web）

版本发布站点 → 签名清单 + JAR → 更新器
管理页面 → 业务端权限校验 → 本机更新器
```

- systemd 只托管更新器，由更新器管理业务子进程；不再同时运行直接托管主 JAR 的旧服务。
- 更新器通过 Java `ProcessBuilder` 启动主进程，JDK 路径、JVM 参数、profile、工作目录均来自本机配置；不执行发布清单提供的命令。
- 更新器停止时须停止并等待子进程退出；更新器崩溃重启时检查已有子进程身份，避免重复启动。systemd 的进程组停止策略与更新器行为一起验证。
- 安装首期只支持已托管的实例，不自动接管未知 Java 进程，不用模糊进程名杀进程。
- 本机通信绑定回环地址并使用本机凭证；浏览器不直接取得更新器凭证。安装前业务端检查平台级权限、执行人及目标发布 ID，租户管理员不可更新整个服务。
- 同一安装目录只允许一个更新器和一个更新任务，用操作系统文件锁保护；安装确认后任务交由更新器持久执行，不依赖原 HTTP 请求存活。

建议目录：

```text
fa-admin-install/
├── updater/fa-admin-updater.jar
├── releases/<releaseId>/fa-admin.jar
├── config/application-prod.yml
├── config/updater.yml
├── data/                         # 上传文件等持久数据，实际路径按部署配置
├── log/
└── update/
    ├── downloads/               # 临时下载 .part 和已校验候选包
    ├── state.json               # 当前版本、上一版本、候选版本及事务阶段
    └── history/                 # 安装记录、备份引用及恢复记录
```

- 各版本目录保留不可变 JAR，切换本地版本指针，不覆盖正在运行的 JAR。
- 状态通过同文件系统临时文件、同步落盘和原子替换提交；不支持可靠原子替换的存储在预检中拒绝自动安装。
- 外置配置、密钥、许可证、上传文件、日志不随 JAR 替换；业务工作目录固定为安装根目录，并显式加载外置配置。
- 首次迁移核对所有相对路径和现有数据目录。保留当前版本、上一成功版本及正在安装的候选版本，不能被清理任务删除。
- 更新器首期不在线自更新，升级更新器使用单独人工维护流程。

## 4. 发布协议与下载来源

首期无需专门开发发布服务：使用独立 HTTPS 静态站点或对象存储，保存不可变发布清单、签名和 JAR；更新站点不能依赖正在被更新的同一业务实例。

每份发布清单至少包含：

| 字段 | 用途 |
| --- | --- |
| productId / edition / channel | 区分业务项目、定制版本和 stable / beta 渠道 |
| releaseId / releaseSequence / versionName | 唯一发布 ID、递增发布序号、展示版本 |
| buildCommit / publishedAt / notes | 构建来源、时间与更新说明 |
| artifactUrl / size / sha256 | 不可变 JAR 地址、大小及哈希 |
| minJava / minUpdater / upgradeFrom | Java、更新器及允许的来源版本要求 |
| databaseTypes / schemaTargets | 数据库支持范围、模块目标 SQL 版本 |
| rollbackCompatibleFrom / requiresManualMigration | 允许自动回退的来源版本、是否需要人工迁移 |
| keyId / signature | 可信发布签名，具体采用分离签名 |

- JAR 内嵌构建元数据，业务端与更新器都能读取真实发布 ID；发布序号独立于各模块 SQL 版本。
- “最新版本”定义为本产品、本定制版本、本渠道、当前环境可升级的最高发布序号，不能简单按文件名或字符串比较版本。
- CI 构建时启用 `-Pfrontend`，检查 JAR 包含前端产物及发布元数据；同一 releaseId 不可重新上传不同内容。
- 发布顺序：上传 JAR → 上传签名版本清单 → 最后更新渠道指针。保留旧发布用于恢复。
- 清单固定字节使用 Ed25519 等签名方案；客户端预置可信公钥，私钥仅放在发布环境。哈希负责完整性，签名负责来源可信，二者都校验。
- 下载 URL 和重定向受信任来源限制，配置超时、大小上限、磁盘检查和重试；候选文件校验通过后才进入可安装状态。
- 初期支持失败重下载；断点续传后续增加，不能复用未经验证的旧下载片段。

## 5. 更新状态与执行流程

```text
空闲 → 检查版本 → 下载中 → 校验通过 / 待安装
     → 安装预检 → 维护与备份 → 停止旧进程
     → 切换候选版本 → 启动与迁移 → 就绪验证 → 成功

下载 / 预检失败 → 保持原版本运行
启动失败 → 按数据库兼容规则回退，或进入“需要人工恢复”
```

1. 检查并展示升级说明、停机提示、兼容性及是否支持自动回退。
2. 更新器下载到临时文件，验证清单签名、大小、SHA-256 和 JAR 元数据；此阶段业务正常运行。
3. 安装前再次检查当前版本、部署模式、维护窗口、启动参数、磁盘空间、数据库方言与迁移要求，阻止重复点击和过期任务。
4. 安装任务落盘后，业务端进入维护状态：拒绝新写操作，暂停定时任务 / 消费者，等待在途任务结束；涉及数据库迁移时完成一致性备份并记录位置。不能完成维护或备份则终止安装。
5. 请求主程序优雅停止；超过超时默认中止，不直接强杀迁移或重要任务。确认旧进程退出后才能启动候选版本。
6. 保存上一成功版本，记录候选版本与安装阶段，然后启动新 JAR；新进程在维护状态下运行已有数据库迁移逻辑。
7. 核验候选进程、发布 ID、启动实例 ID、SQL 升级结果、必要依赖及代表性只读业务检查；连续稳定一段可配置时间后确认成功。
8. 提交当前成功版本，退出维护模式并恢复任务；页面重连后查询最终结果，刷新 Web 资源。
9. 失败时停止候选进程，再依兼容策略恢复。旧版本恢复也必须通过就绪验证，否则停止循环重启并提示人工介入。

就绪结果必须对应本次候选进程，而不是仅判断端口可连接。设计本机受保护的更新就绪接口 / 文件，在 `ApplicationReadyEvent` 后才报告启动完成；数据库及业务检查同时通过才放行。Spring Boot 的该事件发生在 runners 执行后，可与现有 `DbInitRunner` 衔接。

## 6. 数据库升级与回退边界

**JAR 回退不等于数据库回退。数据库兼容性是自动安装的准入条件。**

- 无数据库变更：候选启动失败，可切回上一成功 JAR并验证恢复。
- 向后兼容的新增表 / 列等迁移：只有发布流水线验证旧 JAR 能使用迁移后的数据库，并在清单声明允许的来源版本，才允许自动回退 JAR；数据库保留已执行迁移。
- 破坏性变更、数据转换、不能确认兼容、跨越未支持版本链：首期阻止无人值守安装，转人工维护流程。
- SQL 执行失败可能已经产生部分变更，不能仅根据“迁移失败”判定数据库未改变。需要验证迁移中间状态也兼容旧版，否则保持维护状态并人工恢复。
- 不自动执行反向 SQL，不自动恢复生产数据库备份；恢复备份会涉及数据丢失和外部系统一致性，须单独执行恢复流程。
- 新 SQL 继续使用现有版本头和记录机制，MySQL / PostgreSQL 同步提供；DM8 或其他方言只有发布包具备相应脚本并通过验证才允许更新。
- 数据库升级锁只防并发迁移，不阻止其他实例写业务数据；首期因此限制为单实例，不能将现有锁视为集群更新能力。
- 部署关闭 `startDbInitOnBoot` 时，含未执行 SQL 的版本不能自动安装，需先人工迁移并验证目标数据库版本。

## 7. 页面、接口与自动策略

- 管理菜单建议“系统管理 → 系统更新”，与“数据库升级日志”分开。
- 页面包括当前版本、可用版本、说明、下载进度、安装条件、任务状态与历史；没有更新器时显示接入说明。
- 操作依开发顺序逐步接通：检查版本 → 下载 → 安装 → 设置自动策略。
- 接口按现有 Biz / Controller 风格组织，建议覆盖当前信息、检查、下载、安装、任务状态、历史和策略；业务代码归 `fa-base`，整包构建归 `fa-admin`，新增独立 `fa-admin-updater` Maven 模块。
- 本地任务日志为恢复依据，业务数据库审计记录为页面查询依据；数据库不可用期间仍记录执行结果，服务恢复后按任务 ID 幂等补录。
- 页面开始用轮询展示状态；重启中连接失败显示“服务正在更新”，恢复后查询任务 ID 并刷新，不把断线直接判为安装失败。
- 首期自动检查建议每 6 小时一次并随机错峰；自动安装默认关闭。启用时要求配置明确时区和维护窗口，无窗口不执行无人值守安装。
- 同一失败 releaseId 不自动重复安装；故障后暂停自动安装，允许管理员处理后重试。
- 安装开始后不提供任意中途取消；下载阶段可取消。手动回退也按数据库兼容规则判断。
- 新页面发布后处理 HTML 缓存和前端旧资源错误，更新成功执行页面刷新，避免旧页面继续调用新 API。

## 8. 分阶段开发说明

- 功能 1—2：先做版本展示与检查页；补充构建元数据和发布脚本，用两份测试版本完成“看到可升级版本”的闭环。
- 功能 3：接通独立更新器的下载与进度，校验通过才能出现安装按钮；先验证下载失败不会影响业务。
- 功能 4—5：完成托管启动、外置配置迁移和安装预检，再接页面安装按钮；使用无数据库变更的版本完成完整更新。
- 功能 6：加入数据库兼容策略、失败回退、安装事务日志和重启恢复；先明确恢复判据再开放自动安装。
- 功能 7：补充自动策略页面和 systemd 部署指引，完成隔离环境验收；首次接入检查清单覆盖旧服务停用及数据路径迁移。
- 功能 8—10：Windows、发布中心、容器及集群另行推进，首期页面明确显示支持范围。

## 9. 验证与交付要求

自动验证聚焦签名 / 哈希、版本筛选、状态落盘、并发安装、进程身份、启动失败及恢复规则；更新器使用可控测试子进程验证，不默认运行完整前端构建或全量测试。

人工验收在隔离部署和备份数据库上按顺序执行：

1. 从旧版检查、下载并安装新版，确认后端与 Web 同步升级，配置、许可证和上传文件保留。
2. 下载中断、错误哈希 / 签名、磁盘不足、来源不可信时，确认原服务正常运行且无法安装。
3. 两次同时安装、旧任务再次提交、旧服务未停用时，确认只启动一个业务进程。
4. 候选启动失败 / 就绪超时，确认兼容时恢复旧版，不兼容时保持维护并显示恢复说明。
5. 测试正常 SQL 迁移和部分 SQL 失败，确认没有把数据库状态错误地当作已回退。
6. 安装各关键阶段终止更新器或模拟主机重启，确认日志恢复、进程不重复、失败版本不循环安装。
7. 在维护窗口测试无人值守安装，验证窗口外不安装、关闭策略后不再自动安装。
8. 管理页面在停机时提示更新中，恢复后显示真实结果并刷新资源；普通用户与租户管理员无安装权限。

开发完成的功能先更新为 🔍验证中；人工验证成功并经用户确认后更新为 ✅已完成。

## 10. 实施前需确定的环境信息

本方案按 Linux 单实例部署编写。开始功能开发前需补齐：主要部署系统、现有启动方式、发布站点与产品标识、数据库类型 / 备份方式、数据目录和可接受的维护窗口。若优先 Windows，可调换平台适配顺序；若必须保持直接运行原 `java -jar fa-admin.jar` 的入口，则需要另行设计引导层，而不能假设普通业务 JAR 已具备可靠自恢复能力。
