# DM8 自动升级

状态：🔍验证中（定向测试及只读语法检查；尚未执行真实升级）

## 适用范围

- 当前存量 DM8 数据库已完成基础表迁移，`fa-base` 成功版本至少为 `V1.0.9`。
- 此目录维护 `1.0.10` 起的增量升级，版本与 MySQL 目录对应；不用于从空库初始化。
- 本系统现有实例为 DM8 原生模式（`COMPATIBLE_MODE=0`）、大小写不敏感。表和字段沿用现有命名。
- JDBC 显式配置目标 schema：`jdbc:dm://host:5236?schema=ZDJ_DEV`。路径 `/ZDJ_DEV` 不能代替 schema 参数。

## 执行机制

- `startDbInitOnBoot: true` 后，启动按模块顺序、脚本版本递增执行；`fa-base` 先于业务模块。
- JDBC 产品 `DM DBMS` 对应资源目录 `sql/{模块}/dm8/`，不会回退执行 MySQL SQL。
- 使用 `DBMS_LOCK` 对同一 schema 的升级加锁；数据库账户需要该包的执行权限。
- `base_system_update_log` 中成功版本及以下的脚本跳过；失败立即中止启动。`1.0.27` 之后记录状态、文件名、校验和及耗时。
- 失败脚本可能已提交部分 DDL，不能依赖事务整体回滚；修复原因后重启，从失败版本重试。
- 历史日志按最高成功版本推进，日志与手工迁移必须一致；不要直接把版本改为最新来跳过未完成升级。

## 维护约定

- 每个新版本分别维护 MySQL、DM8 SQL，使用相同文件名版本和 `@@ver`；不要直接复制 MySQL 方言。
- 新表、列和索引使用带当前 schema 条件的 `ALL_*` 元数据检查，匿名块通过 JDBC 整体执行，无需 `/` 分隔符。
- 保留字段备注；JSON/长文本使用 CLOB，自增使用 IDENTITY，显式插入自增 ID 时使用 IDENTITY_INSERT。
- 已存在的菜单保留原配置；`1.0.22` 不导入上游的示例字典 ID 57–61 与示例数据 ID 1–8。
- `admin_enabled` 仅在首次新增字段时回填存量用户，保留手工配置的准入状态。
- 更新审计时间沿用 Java 层自动填充，不依赖 MySQL 的 `ON UPDATE CURRENT_TIMESTAMP`。
- 发布后的脚本保持不变，后续修改新增版本。测试会检查 MySQL 与 DM8 增量版本是否一致。

## 首次启用验证

1. 在数据库副本上确认 schema、版本日志和备份，启动应用执行升级。
2. 检查 `fa-base` 到 `V1.0.51`，`fa-wind-predict` 到 `V1.0.1`；测试登录、权限、字典、消息、Telemetry、日志归档及气象数据。
3. 再次启动，确认成功脚本不重放；在副本上验证失败重试与并发启动。
4. 验证通过后再在生产启动。此目录不执行自动数据回滚。

## 合入 main

DM8 支持可以合入 main，运行时按 JDBC 方言选择 SQL、查询和日志归档实现。后续统一维护 main 与各数据库脚本，无需长期维护 dm8 分支。先完成上述验证，再分别提交 fa-core、fa-base 子仓库的改动，最后更新主仓库的子模块引用；本次未合并或推送分支。
